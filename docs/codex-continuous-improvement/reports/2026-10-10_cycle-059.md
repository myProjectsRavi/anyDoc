# Cycle 059 — Batch queue clear/start integrity

**Status:** ACTIVE / INCOMPLETE
**Epic:** `E059`
**Feature:** `F061`
**User Story:** `US-R059-P1-01A`
**Branch:** `codex/anydoc-continuous-improvement`

## Source evidence
`clearQueue()` checks `isProcessing` on a snapshot, then assigns a replacement `BatchQueueUiState` without compare-and-set. `beginProcessing()` uses a mutex but clear is not under that mutex; its queued task IDs are captured before a separate StateFlow update. Concurrent clearing can drop an active queue or cause processing to start with missing tasks.

## Acceptance
- Clear only when the state being atomically replaced is not processing, retrying on concurrent updates.
- Begin processing only when its exact snapshot is not processing and contains queued tasks; atomically set processing and return IDs from that same snapshot.
- Preserve expected error messages and unrelated state changes, and avoid introducing unbounded spin or blocking the UI.
- Add app JVM regressions for empty queue, active queue, normal clear, and concurrent clear/start; verify exact implementation SHA with authoritative PR CI.
- Keep PR #1 draft/unmerged; never modify main.

## Next exact mutation
Refactor `BatchQueueRuntimeStore.clearQueue` and `beginProcessing` to use snapshot-validated CAS loops; add focused JVM concurrency regressions. No Cycle 059 production/test mutation or CI success is claimed at activation.
